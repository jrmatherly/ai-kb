# Bitbucket Cloud data source connector: design

Date: 2026-10-22, revised the same day after a three-model adversarial review (fable, opus, sonnet). Status: proposed, awaiting review before any code. Companion plan: none yet; it follows review.

## Goal

A `bitbucket` data source connector that syncs document files from the directories of selected Bitbucket Cloud repositories into a knowledge base, with the same user-facing behaviour as the GitHub connector (`internal/datasource/connector/github/`): streaming full sync, incremental sync by commit, deletion tombstones, checkpoints every 50 entries, resume after a timeout, full-sync reconcile, and the shared git-connector form. Bitbucket Data Center is out of scope (decided 2026-10-22; Atlassian stopped issuing self-serve Data Center trial licences on 2026-03-30, so the Data Center path could not be verified against a live instance).

## What exists before this change

- No `bitbucket` string anywhere in the repository. Unlike GitHub, there is no placeholder type constant or metadata entry to flip.
- Three repository-file connectors share `internal/datasource/connector/repofile/` (`NormalizePath`, `CollapsePaths`, `InScope`, `IsSupported`, `KnowledgeRelativePath`). The GitHub connector is the structural model: stateless connector configured per call, `settings.repositories[]` of `{repository, ref, paths}`, a per-repository cursor with a pending checkpoint, `CompleteListing` on a nil-cursor run.
- The Confluence connector (`connector/confluence/`) shares nothing usable. Its edition switch, `_links.next` pagination, page and space models, HTML to Markdown conversion and asset inlining are document-connector concerns; the only overlap with Bitbucket is one Basic-auth call. Reviewed 2026-10-22, file and line in the session notes; the premise that an "Atlassian helper" would serve both is refuted.
- Upstream has no Bitbucket connector, so there is nothing to adopt and the package is our own work.

## Bitbucket Cloud API facts the design rests on

Checked against the official OpenAPI document (`developer.atlassian.com/cloud/bitbucket/swagger.v3.json`), the REST intro and source pages, and live calls to the public repository `atlassian/aui` on 2026-10-22. "Measured" means observed live; everything else is from the documents.

| Need | Endpoint | Fact |
| --- | --- | --- |
| Credential check | `GET /2.0/user` | 401 on a bad token; needs the `read:user:bitbucket` scope |
| Workspaces | `GET /2.0/user/workspaces?pagelen=100` | paged; needs `read:workspace:bitbucket` |
| Repository listing | `GET /2.0/repositories/{workspace}?role=member&pagelen=100` | repositories the token can read in one workspace; no global listing exists |
| Repository | `GET /2.0/repositories/{workspace}/{slug}` | `full_name`, `uuid`, `mainbranch.name`, `links.html.href`; the lookup ignores case and `full_name` carries the canonical lowercase spelling (measured: `Atlassian/AUI` returns `atlassian/aui`) |
| Head commit | `GET /2.0/repositories/{ws}/{slug}/refs/branches/{name}`, then `.../refs/tags/{name}`, then `.../commit/{sha}` for a 40-hex value | `target.hash` (or `hash` for a commit); an unknown name is 404 (measured); a branch name may contain `/` and resolves under `refs/branches` raw or escaped (measured), while `commit/{name}` does not accept such a name (measured) |
| File listing | `GET /2.0/repositories/{ws}/{slug}/src/{commit}/{dir}/?max_depth=50&pagelen=100&fields=values.path,values.type,values.size,values.attributes,next` | breadth-first recursive to `max_depth`, then silently stops; entries are `commit_file` or `commit_directory` and carry `path`, `size`, `attributes` (`link`, `executable`, `subrepository`, `binary`, `lfs`); no blob id; `pagelen` max 100; a listing too deep "will time out and return a 555", there is no truncated flag (measured: 1,959 files in 20 pages); a directory missing at that commit is 404 (measured) |
| Change list | `GET /2.0/repositories/{ws}/{slug}/diffstat/{new}..{old}?topic=false&renames=false&pagelen=100` | `new..old`, the reverse of `git diff` (measured: reversing the spec swaps the `added` and `removed` counts); `topic=false` forces a plain two-dot diff; `renames=false` reports a rename as `removed` plus `added`; entries carry `status` (`added`, `removed`, `modified`), `old.path`, `new.path` (measured: `removed` has `new: null`, `added` has `old: null`); paged; an unknown commit is 404 (measured); a timeout is 555; `path=` matches whole files only, so a diffstat cannot be scoped to a directory (measured); no size, no attributes and no blob id |
| File body | `GET /2.0/repositories/{ws}/{slug}/src/{commit}/{path}` | raw bytes with a content-based `ETag` (measured); `Content-Length` was present without compression (measured with curl) but Go's transport negotiates gzip and then reports no length; a Git LFS file answers 301 to Atlassian's media platform; a symlink's body is the link target path |
| Auth | `Authorization: Basic base64(email:api_token)` or `Authorization: Bearer <token>` | API tokens with scopes replaced app passwords, which were removed on 2026-07-28; workspace, project and repository access tokens are sent as Bearer |
| Host | `https://api.bitbucket.org/2.0` | fixed; there is no enterprise host for Cloud |
| Pagination | `values` plus an opaque `next` URL | "only `values` and `next` are guaranteed"; never build page URLs |
| Rate limit | 429 with the body "Rate limit for this resource has been exceeded" and the headers `x-ratelimit-limit`, `x-ratelimit-remaining`, `x-ratelimit-reset` (seconds until the window resets); no `Retry-After` (measured) | repository data is 1,000 requests per hour per user for the API tokens this cut supports (the scaled limit applies only to access tokens); which group a raw `src` fetch counts against is unverified |
| Identity | `{workspace}/{slug}` or `{uuid}` in braces | the repository `uuid` survives a rename; the slug does not |

## Decisions

1. **One algorithm: list the new head, diff only what both heads hold.** Bitbucket exposes no blob id, so GitHub's SHA snapshot diff is impossible, and diffstat alone carries no sizes or attributes, so it cannot be the only source either. Every run that has work to do takes the recursive listing of each selected root at the new head (about one request per hundred files; measured 20 pages for 1,959 files), keeping `commit_file` entries that are in scope, have a supported extension and carry no `link`, `subrepository` or `lfs` attribute. The listing is the only source of candidates, so size and attribute checks happen before any fetch in every mode. The change set is then:
   - *Tombstones.* Paths the index holds that the new listing does not: when the ref is unchanged, the `removed` entries of `diffstat/{head}..{recorded head}?topic=false&renames=false` that are in the recorded scope, plus the listing of each root that left the selection taken at the recorded head; when the ref changed or the recorded head is gone, the whole listing at the recorded head with the recorded roots, under the recorded ref. A 404 on that listing (the commit was garbage-collected) logs and yields no tombstones.
   - *Items.* When the ref is unchanged and the recorded head exists: the `added` and `modified` entries of the same diffstat that are in the new listing, plus every new-listing path in a root that entered the selection. Otherwise every path of the new listing.
   - *Unknown change set.* A diffstat that times out (555) or whose commits are gone (404) makes the change set unknown: every path of the new listing is an item, and the tombstones come from the listing at the recorded head where it is readable. That costs one fetch per file but always terminates and resumes from checkpoints; there is no smaller diffstat to fall back to (measured: `path=` cannot scope one to a directory).
   - A listing that times out (555) is retried one directory at a time with `max_depth=10`, descending only into directories that lead to or lie inside a selected root; a 555 on a single directory fails the sync, since a listing missing files would tombstone them. A `commit_directory` at the depth limit of any listing fails the sync for the same reason, so a tree deeper than the limit is never silently truncated. A root that is 404 at a resolved commit is an empty root, not an error, so a directory deleted upstream tombstones its files instead of wedging the sync.
   - Emission order is deterministic: tombstones sorted by path, then items sorted by path. That is what makes the pending offset valid. The first sync, a ref change and a missing recorded head are the degenerate cases of the same rule with an empty intersection.
2. **A pending run is always finished first.** GitHub needs its overlay chain because its baseline is a snapshot. Here the baseline is a commit, so an interrupted run is simply completed before anything else: the retry recomputes the same change list for the pending `{head, ref, paths}` against the recorded baseline (both commits still exist), emits the entries from `done` on, and records the pending head, ref and paths as the completed baseline. Only then is the current selection reconciled by decision 1 against that baseline. This holds whatever changed in the meantime (the head moved, the ref or directories changed, or nothing), so the one pending slot is always drained before a new change list starts, nothing emitted by an interrupted run is left without its tombstone, and no path is tombstoned that the same run re-emits. Everything emitted is exactly what a sync to the pending selection followed by a sync to the current one would emit. The cost is fetching the rest of an abandoned selection once, and fetching twice a file that changed between the pending head and the new head; that is intended and cheaper than the chain. If the recorded baseline commit is gone when a pending run resumes, the change list's definition changed, so the resume restarts at `done = 0` (re-emitting is idempotent, skipping is not). If the pending head itself is gone, the pending is dropped with a warning and the run falls back to decision 1 against the recorded baseline; paths the interrupted run added that the new head lacks then stay until a full-mode sync with deletion sync on, the same documented gap GitHub has past its chain cap. The pending record is `{head, ref, paths, done}`.
3. **Repository key is the lowercased `workspace/slug`.** Lookups ignore case and `full_name` comes back lowercase, so the key is normalised as GitHub's is (trimmed, lowercased, stripped of a trailing `.git`, a URL rejected, exactly one slash, each part matching `^[a-z0-9._-]+$`). The `uuid` is recorded in item metadata only. A renamed repository changes its key and is treated as a removed plus an added selection; the docs say so.
4. **File cap is 100 MB of our own, checked from the listing; LFS and symlinks are skipped there too.** Every candidate comes from the new-head listing (decision 1), which carries `size` and `attributes`, so a file over the cap is reported as a per-item failure (`bitbucket_file_too_large`, "exceeds the 100 MB import cap") without a request, and an entry with the `lfs`, `link` or `subrepository` attribute is skipped without a request, as GitHub skips symlinks and submodules. The raw fetch still reads through a capped reader, which is the contract (the shared client negotiates gzip, so `Content-Length` is not reliable); an overrun there is the same per-item failure. The raw fetch uses a client whose `CheckRedirect` returns `http.ErrUseLastResponse`, so a 3xx (an LFS pointer the listing did not flag) is reported as `bitbucket_lfs_unsupported` instead of being followed off host by the shared client's redirect policy. The two reason codes live in `SyncReasonTexts`, are checked by `internal/datasource/syncreason/parity_test.go`, and have `datasource.syncError.*` keys in `en-US.ts`. Path segments are percent-escaped in every `src` URL.
5. **Credentials are `username` (optional) and `access_token`; no base URL; Validate checks the selection.** A username present means Basic auth with the Atlassian account email and an API token, the form Atlassian documents since app passwords were removed; no username means Bearer. The host is fixed, so there is no `base_url` field, no `normalizeBaseURL`, and no SSRF validation of user input; the client is still built on `datasource.NewConnectorHTTPClient` with a 30 s timeout. `Validate` fetches the first selected repository (`GET /repositories/{ws}/{slug}`, the call every sync opens with) when a selection exists and `GET /user` only when none does, so an API token needs `read:repository:bitbucket`, plus `read:workspace:bitbucket` only to browse repositories in the picker; the form's hint says so. Whether an API token also works as a bare Bearer value, and whether workspace, project and repository access tokens pass this Validate, is checked in the live run with a real token and recorded in the docs.
6. **Rate limiting is not a permission error, and the reset header is the signal.** A 429 maps to `errRateLimited` carrying the `x-ratelimit-reset` time, never to `datasource.ErrPermissionDenied`; a 403 stays `ErrPermissionDenied`, a 401 `ErrInvalidCredentials`, a 404 `ErrResourceNotFound`, as in the GitHub client. There is no `Retry-After` on Bitbucket's 429 (measured), so GitHub's retry-once branch is not copied. When the reset is at most 30 minutes away the run waits for it once (inside the two-hour task timeout) before continuing, so a forced full sync of a mid-sized repository can finish on its first attempt and reconcile; otherwise the run ends and the checkpoint resumes it. Every supported token sits in the 1,000 requests per hour group, so a first sync of more than about a thousand files spans several runs; the docs say so.
7. **Pagination follows `next` only**, with GitHub's three guards: a repeated URL is an error, more than 10,000 hops is an error, and a `next` that does not start with `https://api.bitbucket.org/2.0/` is an error, so the token never travels off host. The `fields` parameter trims every paged response to the fields the connector reads.
8. **A full sync is a complete listing.** The metadata entry declares `incremental`, `hierarchical`, `deletion_sync` and `full_sync_reconcile`, and a run that started from a nil cursor and whose listings all completed returns `CompleteListing`, so the service deletes what the run did not emit. The service passes a nil cursor on the first attempt of a forced full sync only and tracks emitted ids per run, so a forced full sync that is cut by the hourly limit and resumed never reconciles (a cursor marker cannot fix that: the resumed run's emitted set lacks the first attempt's items and reconcile would delete them). Decision 6's wait makes that rare for repositories under a few thousand files; the docs state the limit. The datasource tests' `reconciles` map gains the type and, like GitHub, it is excluded from the tracks-source assertion.
9. **Removed repositories are tombstoned from their recorded listing, and a gone repository is dropped.** A repository in the cursor but no longer selected has its listing at the recorded head and paths tombstoned under the recorded ref, then, if a pending exists, the pending listing under the pending ref (skipping paths already tombstoned under the same ref), and its entry dropped. A 403 or 404 on the repository or on either recorded commit drops the entry with a warning, because deletion and renaming are the ordinary reasons a repository leaves the selection and keeping the entry would fail every later sync with no operator fix (GitHub's `removeRepository` already treats a gone commit this way; a bad token on Bitbucket answers 401, measured, so 403 alone could never fire). A 5xx, 555 or 429 keeps the entry so a transient failure does not orphan the items.
10. **Frontend reuses the GitHub settings keys.** The selection shape is `settings.repositories[].repository`, identical to GitHub's, so `bitbucket` joins `isGitConnector` and the three per-type ternaries in `DataSourceEditorDialog.vue` (`gitSettingsKey`, `gitItemKey`, `gitLabelsKey`) become one lookup table keyed by type, with `bitbucket` mapping to `repositories`, `repository` and its own label group `datasource.bitbucket` (placeholder `workspace/repository`). The credential form shows `username` (optional, with a hint) and `access_token`. The channel maps in the five document views, the source filter in `KnowledgeBase.vue`, `datasourceIcons.ts` and `en-US.ts` gain the type; `localeKeyAudit.test.ts` asserts the label group matches GitLab's plus the Bitbucket-specific keys.
11. **Icon is the official Atlassian tile, unmodified, with provenance recorded.** Atlassian's trademark guidelines allow third parties to use product logos for related products if the asset comes from an official Atlassian site and is reproduced without modification. The asset is the isolated Bitbucket logomark from `atlassian.design/resources/logo-library`, the same tile style as the Confluence icon already in the repo, so it needs no dark-mode invert rule. A new `frontend/src/assets/img/ICONS.md` lists the Bitbucket mark's source URL and the guideline it was checked against. Replacing the GitHub mark (today the Simple Icons tracing) with the Invertocat from GitHub's own `GitHub_Logos.zip` is trademark housekeeping with no dependency on this connector and goes in its own commit before this change, adding its own row to `ICONS.md`.
12. **Default-enabled.** `bitbucket` joins `DefaultConnectorTypes` with Notion, Confluence and GitHub in the same PR, so the eleven-file default-enable surface from the GitHub follow-up (`.env.example`, `docker-compose.yml`, `helm/README.md`, the datasource tests, three docs pages, the upstream-review table, the changelog) is part of this change. A deployment that sets `AIKB_DATASOURCE_TYPES` must list it.
13. **Copy, do not extract.** Bitbucket becomes the third copy of the capped reader, the status-to-sentinel error type, the config paths loop and the empty-file body that GitHub and GitLab already duplicate. The GitHub design left them per connector on purpose; extracting them into `repofile` would widen this change into both other connectors for no behaviour change. It is the follow-up to take if a fourth git host ever arrives.

## Data shapes

Credentials: `{"username": "", "access_token": "<token>"}`; `username` optional.

Settings: `{"repositories": [{"repository": "workspace/slug", "ref": "main", "paths": ["docs"]}]}`. `repository` is required and unique after normalisation (decision 3). `ref` empty means `mainbranch.name`. `paths` are forward-slash relative directories, normalised and collapsed by `repofile`; empty means the whole repository.

Cursor: `{"repositories": {"workspace/slug": {"head": "<hash>", "ref": "main", "paths": ["docs"], "pending": {"head": "<hash>", "ref": "main", "paths": ["docs"], "done": 120}}}, "raw": "<json>"}`; `pending` is absent once a repository is complete. `ref` empty in the settings resolves to `mainbranch.name`; a repository whose `mainbranch` is null (empty repository) lists as empty.

Item: `ExternalID` `bitbucket:https://api.bitbucket.org/2.0:<workspace/slug>:<ref>:<path>` (the fixed base is embedded so a later Data Center variant cannot collide); `Title` `<full_name>/<path>`; `FileName` `repofile.KnowledgeRelativePath(<slug>, ref, path)`; `ContentType` `text/plain`; `SourceResourceID` `<workspace/slug>`; `Metadata` `channel=bitbucket`, `source_type=bitbucket`, `bitbucket_repository` (`full_name`), `bitbucket_repository_uuid`, `bitbucket_ref`, `bitbucket_path`, `bitbucket_url` (`<links.html.href>/src/<ref>/<path>`). `UpdatedAt` stays unset. A zero-byte file is emitted with `# <title>` as its body, as GitHub does. A deletion is `IsDeleted: true` with the same `ExternalID`. A per-item failure has the same `ExternalID` and `Title`, no content, and `Metadata` `channel`, `source_type`, `bitbucket_path`, `error`, `error_reason_code`, `error_reason`.

Resources: root lists every repository of every workspace the token can list as `{ExternalID: <workspace/slug>, Name: full_name, Type: "repository", URL: links.html.href, HasChildren: true}`; a parent `workspace/slug[:dir]` lists its subdirectories on `mainbranch`, resolved to its commit hash first because a branch name may contain `/`, through `src/{hash}/{dir}/?q=type="commit_directory"` as `{ExternalID: "workspace/slug:<path>", Type: "directory", ParentID: parent, HasChildren: true}`.

- Live check against a real workspace with an API token pasted into the form, as the GitHub connector was checked on the cluster: first sync of a `docs/` directory, incremental after one commit that adds one file and removes another (the diffstat direction tripwire), a rename plus an emptied file, a branch change, a directory-list change, a forced full sync, the token as a bare Bearer value, and the sync logs from `GET /api/v1/datasource?kb_id=...`.

## Known limitations

- A forced full sync that the hourly limit cuts and a later run resumes never reconciles deletions (decision 8); the next forced full sync that completes in one attempt does.
- A diffstat or listing that times out (555) is recovered by re-fetching every in-scope file of the new listing (decision 1), one request per file.
- Every supported token sits in the 1,000 requests per hour group, so a first sync of more than about a thousand files spans several runs (decision 6), and a tree whose per-directory fallback listing alone exceeds the hour cannot reach its first emit.
- An LFS file is reported as a failed item, not imported (decision 4).
- A renamed repository is a removed plus an added selection (decision 3); the old key's items are tombstoned only while its recorded commit is still readable.
- A pending run whose head commit is gone leaves the paths it added that the new head lacks until a full-mode sync with deletion sync on (decision 2).
- Items of a ref or directory that is no longer selected are removed by the next sync while the source is synced, or by a forced full sync if the selection changed while the source was paused, as for GitHub.

## Out of scope

Bitbucket Data Center and Server; OAuth 2.0 sign-in; pull requests, issues and wikis; Git LFS content; the archive download as a bulk fetch path (one zip per commit in a 1,500 per hour group; worth one authenticated experiment before the plan, not part of this design); extracting the duplicated client helpers into `repofile`; replacing the GitHub icon (its own commit); changing the home-cluster `AIKB_DATASOURCE_TYPES` value (another repository).

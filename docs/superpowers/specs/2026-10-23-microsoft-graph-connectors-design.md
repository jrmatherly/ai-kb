# OneDrive and SharePoint data source connectors: design

Date: 2026-10-23, revised the same day after a three-model adversarial review (fable, opus, sonnet) of the plan and a compile-and-test pass of the plan's code. Status: implemented on the branch `feat/microsoft-graph-datasources` (2026-10-23). Companion plan: `../plans/2026-10-23-microsoft-graph-connectors.md`.

Review added three things this design does not describe. The connector implements `datasource.FullStreamingConnector`, so a full sync runs through the resync path (every selected root restarts its enumeration with a new generation, unchanged files are re-fetched, and what the fresh enumeration does not list is tombstoned at the root's delta link), and a timed-out full attempt resumes from its checkpoint. `Validate` with credentials only mints a token, and when `user` or `site_url` is present it also resolves the drive or the site and its document libraries. `CompleteListing` is true for a fresh first run without a 410 and for a full run that started from scratch in that attempt, false for any resumed attempt (`stream()` in `internal/datasource/connector/msgraph/sync.go`).

## Goal

Two data source connectors, `onedrive` and `sharepoint`, that sync document files from Microsoft 365 into a knowledge base over the Microsoft Graph API: OneDrive for work or school (one user's drive, selected folders) and SharePoint Online (one site, selected document libraries and folders). Same user-facing behaviour as the Seafile connector: a folder tree picker, streaming sync with checkpoints and resume, incremental sync, deletion tombstones, full-sync reconcile, per-file error items. The two types share one Go package because they share the API, the token exchange and the sync algorithm; only the root of the tree differs.

## What exists before this change

- `types.ConnectorTypeOneDrive = "onedrive"` (`internal/types/datasource.go:35`) and a catalog stub in `ConnectorMetadataRegistry` (`internal/datasource/connector.go:332`, name "OneDrive / SharePoint", `AuthType: "oauth2"`, capabilities `["incremental"]`, priority 6). No package, no registration, no form, no icon, no strings. `internal/datasource/README.md:7`, `website-docs/03-features/10-datasource.md:473` and `website-docs/06-development/03-extension-points.md:506` say it is not implemented. `frontend/src/utils/channelLabel.test.ts:14` exempts `onedrive` from needing a channel label. There is no `sharepoint` constant anywhere.
- The sync engine contract (`internal/datasource/connector.go`): every production connector implements `StreamingConnector.FetchStream`; `StreamHandler.Checkpoint` persists the connector cursor together with the service's pending deletions in one write; tombstones are deferred to `settleDeletions`; a run whose returned cursor has `CompleteListing` set, in a data source whose `sync_mode` is `full` and whose type declares `full_sync_reconcile`, deletes every owned item the run did not emit. The service never skips an emitted item as unchanged: every live `Emit` is delete plus recreate plus re-parse, so the connector alone decides what not to re-emit.
- Three file-shaped precedents. Seafile (`connector/seafile/`) is the cloud-storage template: per-file fingerprint map in the cursor, download link fetched by a second, unauthenticated client, size cap from `utils.GetMaxFileSize()`, error items with reason codes. Bitbucket (`connector/bitbucket/`) is the template for a fixed API host with a test override, the status-to-sentinel error type, the capped reader, the 30-minute rate-limit wait. Feishu/Lark (`connector/feishu/`) is the template for two connector types sharing one package through a value fixed at construction (`core.Region`).
- Token exchange precedents are in-memory and per run: Feishu `GetTenantAccessToken` (mutex, cached until expiry minus a 5-minute skew, invalidate on a rejected token), DingTalk `accessToken` (same, no mutex, 401 retried once). No connector persists anything back into its credentials; the `Connector` interface receives a decrypted copy of the config and has no repository handle. The only OAuth-with-user flow in the server is the MCP service OAuth (`internal/mcp/oauth_*.go`), coupled to mcp-go, dynamic client registration and MCP token rows; it is a design template, not reusable code.
- Credentials are a free `map[string]interface{}`; string values are AES-GCM encrypted at rest when `SYSTEM_AES_KEY` is set; `HasConfiguredCredentials` is `len(Credentials) > 0` for every type but RSS. `ValidateCredentials` and the frontend's "Test connection" call `Validate` with credentials only, no settings and no resource ids.
- The frontend has two editor styles decided by hard-coded type checks in `DataSourceEditorDialog.vue`: the lazy tree picker (Feishu, Notion, Seafile and others; children loaded by `parent_id`, selection saved as a minimal cover set into `resource_ids`) and the repository-row form (`gitConnectorKeys.ts`, git hosts only). A connector whose first `ListResources("")` answer carries no `parent_id` gets lazy loading; one that returns any `parent_id` is treated as a full tree.
- Microsoft's product icons are licensed marks: "our logos, app, product icons ... can never be used without an express license" (Microsoft Trademark and Brand Guidelines, quoted on learn.microsoft.com/azure/communication-services/concepts/teams-interop); the Microsoft 365 architecture icon set is permitted "in architectural diagrams, training materials, or documentation" only. `frontend/src/assets/img/ICONS.md` records every third-party mark's source and terms.

## Microsoft Graph facts the design rests on

All from learn.microsoft.com on 2026-10-23 (the `driveItem: delta` page, the scan-guidance page "Best practices for discovering files and detecting changes at scale", the permissions reference, the client-credentials and device-code pages, the throttling pages). Nothing has been measured against a live tenant yet; the plan's last task does that.

| --- | --- | --- |
| App-only token | `POST https://login.microsoftonline.com/{tenant}/oauth2/v2.0/token` with `grant_type=client_credentials`, `client_id`, `client_secret` (URL-encoded), `scope=https://graph.microsoft.com/.default` | Response `{token_type, expires_in (3599), access_token}`; no refresh token; re-mint on expiry. | Read files, app-only | `Files.Read.All` (all drives in the tenant) or `Sites.Read.All` (all sites) or `Sites.Selected` (only sites an admin granted) | `Sites.Selected` is least privilege but a broader permission on the same app overrides it; the grant is a `POST /sites/{id}/permissions` by an admin with `Sites.FullControl.All`; `GET /sites?search=` does not work with `Sites.Selected` |

| Enumerate and track changes | `GET /drives/{driveId}/root/delta`, `GET /drives/{driveId}/items/{itemId}/delta` (the folder form appears in Microsoft's own SDK snippets on the delta page) | pages of `driveItem` with `@odata.nextLink`, then one `@odata.deltaLink`; call `delta` with no token for the initial enumeration ("the only way to guarantee that you've read all of the data you need"); deleted items carry a `deleted` facet; "the same item may appear more than once ... use the last occurrence"; `parentReference.path` is not populated ("always track items by id"); a folder rename returns no descendants; `cTag` is omitted for OneDrive for Business and SharePoint; `$select` and `$top` supported; a delta request with a token costs 1 SharePoint resource unit, without a token 2 |
| Expired delta token | `HTTP 410 Gone` with `resyncChangesApplyDifferences` or `resyncChangesUploadDifferences` and a `Location` header holding a fresh start link | restart the enumeration from that link and compare with local state |
| Current token only | `delta?token=latest` | empty page plus a `deltaLink`; not used here |
| Download | `GET /drives/{driveId}/items/{itemId}/content` answers `302 Found` with a pre-authenticated `Location`; the same URL is `@microsoft.graph.downloadUrl` on the item | the URL needs no `Authorization` header and expires within about an hour; `Range` requests are honoured on the URL, not on `/content` |
| Item facets | `file` (with `mimeType`, `hashes.quickXorHash`, `hashes.sha1Hash`, `hashes.sha256Hash` where available), `folder`, `deleted`, `package` (OneNote notebooks), `remoteItem` (shared items from another drive), `malware` | only items with `file` are downloadable; a `remoteItem` placeholder's contents are not in this drive's delta ("a separate call to delta ... is required for each shared folder") |
| Throttling | `429 Too Many Requests` or `503 Service Unavailable` with `Retry-After` (seconds) | limits are per app per tenant across sites and drives; throttled requests still count; "pause all further requests" while waiting; SDKs and Microsoft's guidance: wait exactly `Retry-After`, exponential backoff only when the header is missing |
| Hosts | `https://graph.microsoft.com/v1.0`, `https://login.microsoftonline.com` | fixed for the global cloud; national clouds use other hosts |

## Decisions

1. **One package, two types, a `kind` fixed at construction.** `internal/datasource/connector/msgraph/` exports `NewConnector(kind)` with `KindOneDrive` and `KindSharePoint`; `Type()` returns `types.ConnectorTypeOneDrive` or the new `types.ConnectorTypeSharePoint = "sharepoint"`. The kind decides the settings key, the tree root and the strings; the Graph client, the token exchange and the delta sync are one code path. This is the Feishu/Lark shape, not two packages, because unlike wiki versus drive the two products expose the same `drive` and `driveItem` resources.

2. **App-only client credentials in this cut; delegated sign-in is a follow-up.** Credentials are `tenant_id`, `client_id` and `client_secret`, all three in `Credentials` so the credentials-only `Validate` can mint a token (the frontend's "Test connection" sends no settings). The connector mints an access token per run and caches it on the client behind a mutex until `expires_in` minus five minutes, re-minting once on a 401 (Feishu's `GetTenantAccessToken` shape). Nothing is persisted. This fits the codebase as it is: no new routes, no token table, no credential writeback. It covers SharePoint Online and OneDrive for work or school, which is what an organisation deploying AI KB has. It does not cover personal OneDrive (`onedrive.live.com`): that needs a delegated flow with a rotating refresh token, which needs a writeback path the `Connector` interface does not have and either a public callback route or a device-code poller in the editor, modelled on `internal/mcp/oauth_lifecycle.go`. The docs say so in one sentence; the catalog name becomes "OneDrive (work or school)". Reversible on Jason's word: a delegated cut would add `auth_mode` to the credentials and leave this design's sync untouched.

3. **Least privilege is the operator's choice, the connector asks for a URL or a user, never for the tenant list.** The form documents two app-registration recipes. SharePoint: `Sites.Selected` plus a per-site grant (least privilege), or `Sites.Read.All`. OneDrive: `Files.Read.All` (the only app-only way into a user's drive; it is tenant-wide and the hint says so). Because `Sites.Selected` forbids `GET /sites?search=`, the connector never lists sites: the SharePoint settings carry `site_url` (`https://contoso.sharepoint.com/sites/hr`), resolved with `GET /sites/{hostname}:/{path}`, and the OneDrive settings carry `user` (UPN or object id), resolved with `GET /users/{user}/drive`. Both are public settings the way Confluence's `base_url` and `username` are: the editor shows them in the credentials step, mirrors them into `settings` on every submit, test and listing, and hydrates them back from `settings` on edit (the existing `syncConfluencePublicFieldsToSettings` pair becomes one table-driven pair covering Confluence, OneDrive and SharePoint). The connector reads them from `Settings` and falls back to `Credentials`, which is where they arrive during "Test connection". `Validate` resolves the root when the field is present (that is the call every sync opens with); with the three credentials alone it mints a token and stops. Token-endpoint errors (`invalid_client`, `unauthorized_client`, `AADSTS7000215`, `AADSTS700016`, `AADSTS90002`) map to `datasource.ErrInvalidCredentials`; Graph 401 to `ErrInvalidCredentials`; 403 to `ErrPermissionDenied`; 404 on the root to `ErrResourceNotFound`; a malformed `site_url` to `ErrInvalidConfig`.

4. **The tree is drives and folders; files are not pickable.** `ListResources("")` returns, for SharePoint, the site's document libraries (`GET /sites/{id}/drives`, one resource per drive, `has_children: true`, `type: "drive"`), and for OneDrive the single drive. A non-empty parent lists that node's child folders only (`GET /drives/{d}/items/{i}/children?$select=id,name,folder,lastModifiedDateTime,webUrl&$top=200`, folders filtered client-side, paged by `nextLink`). Resource ids are `<driveId>` for a drive root and `<driveId>:<itemId>` for a folder (drive ids contain no colon; the split is at the first colon). `ResolveResourceAncestors` walks `parentReference.id` with `GET /drives/{d}/items/{i}?$select=id,parentReference` per hop (Feishu wiki does this on demand). Files are not pickable because a delta root is a folder; selecting single files would need a second, non-delta code path for no user gain. Duplicate ids are dropped at parse time; an empty selection parses (the credentials-only `Validate` has none) and is `ErrInvalidConfig` when a sync starts. A root nested under another selected root cannot be recognised from the ids alone (unlike Seafile's path ids) and is tolerated: the picker's minimal cover set normally prevents it, and when it happens the fingerprint map (decision 6) makes the second stream skip what the first already emitted and a deletion seen twice costs one `Skipped` count. The first-level response carries no `parent_id`, so the picker lazy-loads.

5. **One delta stream per selected root, resumed by link.** For each root the connector calls `delta` with `$select=id,name,size,file,folder,deleted,parentReference,eTag,lastModifiedDateTime,webUrl,package,remoteItem` and walks `nextLink` pages. The cursor per root is `{delta: "<deltaLink>", next: "<nextLink in progress>"}`: `next` is written by `Checkpoint` only after every item of the page it follows has been emitted, so a resumed run continues at the first unprocessed page; `delta` replaces `next` when the final page arrives. On an interrupted run the next attempt resumes `next`; nothing is re-emitted. A 410 on either link restarts that root from the `Location` link with `resync: true` on the root; the known-item set (decision 6) turns the restart into a correct diff (every known item not seen by the end of the restarted enumeration is tombstoned). Links are opaque URLs; the connector only follows ones whose prefix is the Graph host, as the git connectors guard their `next`.

6. **The cursor holds a fingerprint per known item so unchanged files are not re-ingested and deletions survive a resync.** Delta reports an item for any change (rename, move, sharing, metadata). The service re-parses and re-embeds every emitted item, so the connector keeps `items: map[externalID]{fp, parent, name, root}` and `folders: map[externalID]{parent, name, root}` and emits a file only when its fingerprint differs from the stored one. The fingerprint is `quickXorHash` when present, else `sha1Hash`, else `sha256Hash`, else `eTag`, joined with `size`, `parentReference.id` and `name`, so a rename or move re-emits (the knowledge file name changes) while a sharing change does not. The maps are the same O(files) cost Seafile already pays (`files map[path]fingerprint`); at about 550 bytes per file with SharePoint-length drive and item ids, 10,000 files make a cursor of about 5.5 MB of JSONB, written at every checkpoint, which the docs note as the practical ceiling per data source. The maps also give the folder path that `parentReference.path` does not: the knowledge file name is `<drive name>/<folder names from root>/<file name>` built by walking `parent` ids through `folders` (the drive root item, marked by its `root` facet, contributes no segment), sanitised with `datasource.SanitizeFileName` per segment. A folder entry arriving after its children in the same page is handled by applying the whole page to the maps before emitting (last occurrence of a repeated id wins); a parent that only arrives on a later page is fetched by id before its file is emitted. A folder rename or move re-sends no descendants, so their stored paths stay until they next change; the docs say so. Each entry also carries the generation of the enumeration that last listed it: a restart after a 410 bumps the root's generation, stamps what it lists, and at its end tombstones every entry under the root with an older stamp, so a restart cut by a checkpoint resumes without forgetting what it saw. A deterministic failure (too large, empty, malware) keeps the fingerprint with a `failed` code and is reported once; a transient one leaves the fingerprint empty for the retry pass.

7. **External id is `<driveId>:<itemId>`, never a path.** A `deleted` entry carries the id and little else, so a path id could not be tombstoned. Rename and move keep the id and are in-place updates. The drive id is part of the id because `ExternalID` is unique per data source and a SharePoint source spans several drives. Items without a `file` facet (folders, `package` items such as OneNote notebooks, `remoteItem` placeholders) are never ingested; folders update `folders`, the others are skipped and counted once in the docs as a limitation (shared folders from another drive are not followed). A `file` item whose name fails `ds.Importable` is not downloaded and not stored in `items`, so its later deletion is not tombstoned (the guide's rule). An item carrying the `malware` facet is an error item (`msgraph_malware_detected`), never downloaded.

8. **Tombstones follow the engine's deferral; folder deletions fan out from the maps.** A `deleted` file entry whose id is in `items` emits `FetchedItem{ExternalID, IsDeleted: true, Title: <stored name>, Metadata{channel: <type>, msgraph_path: <stored path>}}` and removes the entry. A `deleted` folder entry tombstones every `items` entry whose ancestor chain through `folders` reaches it, then removes the folder and its subtree from the maps; the docs do not promise descendants arrive as their own `deleted` entries, and tombstoning an id twice costs one `Skipped` count, nothing more. An id that is not in the maps is dropped silently (it was never ingested). A root that left the selection has every `items` entry under it tombstoned, except entries another selected root still covers (re-homed to that root), and its cursor entry removed before the remaining roots run; a root that joined starts a fresh enumeration. A `deleted` entry for an item another root's stream has since claimed (a move between two selected folders) is ignored, so the file survives whichever stream runs first. A file renamed to a name the knowledge base cannot import is tombstoned. This gives correct deletions in incremental mode, which the engine's own reconcile (full mode only) cannot.

9. **Download is a 302 the connector resolves itself, then an unauthenticated fetch with a cap.** For each file to emit: `GET /drives/{d}/items/{i}/content` on a client whose `CheckRedirect` returns `http.ErrUseLastResponse` (Bitbucket's `rawHTTP`), read `Location`, require `https`, run `utils.ValidateURLForSSRF` on it, fetch it with a second client built without the bearer token (Seafile's `files` client, 120 s timeout) through a reader capped at `utils.GetMaxFileSize()`; a `size` above the cap from the listing is an error item (`msgraph_file_too_large`) before any request; a body whose length differs from `size` is `msgraph_source_changed`; an empty body is `msgraph_empty_file` (Seafile's choice, so an emptied document is reported rather than silently left indexed); a non-302 answer or a redirect to a non-https URL is `msgraph_invalid_response`; a credential, rate-limit, cancellation or transport failure ends the run instead of becoming an error item. `ContentType` is `http.DetectContentType(body)`; `FileName` is decision 6's path; `Title` is the file name; `URL` is `webUrl`; `UpdatedAt` is `lastModifiedDateTime`; `SourceResourceID` is the selected root id; `Metadata` carries `channel`, `msgraph_drive_id`, `msgraph_item_id`, `msgraph_path`, `msgraph_web_url`. The download URL is never logged or stored. A transiently failed download is an error item whose entry keeps an empty fingerprint, so the next run re-fetches it with `GET /drives/{d}/items/{i}` (delta will not re-send an unchanged item) before walking delta; the plan calls this the retry pass, and a per-item failure there (a 403 under `Sites.Selected`) is an error item, not a failed run.

10. **Throttling waits once, then yields to asynq.** A 429 or 503 with `Retry-After` at most 30 minutes is waited for once per run (Bitbucket's `rateLimitWaitMax`), inside the two-hour task timeout, then the request is repeated; a second one, or a longer wait, returns `errRateLimited`, and the next attempt resumes from the last checkpoint. A 429 or 503 without `Retry-After` backs off 2, 4, 8 seconds, three attempts. No checkpoint is taken on an error; what survives is the last checkpoint, taken after the previous page or the previous 50 emits. The delta walk has the same repeated-link and hop guards as the collection pager. Pagination has the git connectors' guards: a repeated link is an error, more than 10,000 hops is an error, a link off the Graph host is an error.

11. **Complete listing on a fresh enumeration; the maps make incremental deletions correct anyway.** The metadata entries declare `incremental`, `hierarchical`, `deletion_sync`, `full_sync_reconcile` and `source_identity_dedup`. A run that started from a nil cursor and whose every root reached its `deltaLink` without a 410 returns `CompleteListing: true`, and so does a full run (`FetchFullStream`) that started from scratch in that attempt, so a `full`-mode data source gets the engine's reconcile as well. A resumed attempt or an incremental run returns `false`. `source_identity_dedup` matters here more than for git hosts: the same PDF in two libraries is normal on SharePoint, and without the capability the second copy is dropped by the knowledge-base-wide hash check. Items emit `metadata["channel"]` equal to their own type, which is what the capability lookup keys on. Neither type declares `selection_tracks_source` (the engine's deselect handling is full-mode only; decision 8 handles deselection itself), matching Seafile.

12. **Fixed hosts, shared SSRF client, test override.** `const graphBaseURL = "https://graph.microsoft.com/v1.0"` and `const loginBaseURL = "https://login.microsoftonline.com"`; `NewConnector(kind)` stores both and tests build `&Connector{graphBaseURL: server.URL, loginBaseURL: server.URL}` behind `allowLocalServer(t)` copied from `bitbucket/client_test.go`. API calls go through `datasource.NewConnectorHTTPClient(30 * time.Second)`; JSON bodies are read through the capped reader at 16 MiB. There is no `base_url` setting and no national-cloud support in this cut; the docs say so. The package copies, and does not extract, the capped reader, the status-to-sentinel error type and the `collector` that GitHub, Bitbucket and Seafile each carry (the Bitbucket design's decision 13 still holds: a shared helper is the follow-up if a fifth copy ever appears).

13. **Error items and codes.** `SyncReasonTexts` in the package: `msgraph_file_too_large`, `msgraph_empty_file`, `msgraph_source_changed`, `msgraph_fetch_failed`, `msgraph_permission_denied`, `msgraph_not_found`, `msgraph_malware_detected`, `msgraph_invalid_response`. Each is a `datasource.syncError.*` key in `en-US.ts` and the list joins `internal/datasource/syncreason/parity_test.go`. API bodies and URLs never reach the sync log (Seafile's `transportError` rule).

14. **Frontend: tree picker, two connector defs, no git-table rows.** `connectorDefs` gains `onedrive` and `sharepoint` entries with the three credential fields (`tenant_id`, `client_id`, `client_secret` secret) plus one public field each (`user`, `site_url`) declared in the same `fields` list and mirrored into `settings` by the table-driven public-fields pair of decision 3, and `requiredPermissions` text per decision 3. The tree picker needs no change. `datasourceIcons.ts`, `channelLabel.ts` (`onedrive` and `sharepoint` after `seafile`), `knowledgeBase.channelOneDrive`, `knowledgeBase.channelSharePoint`, `datasource.connector.*`, `datasource.connectorDesc.*`, `datasource.onedrive.*` and `datasource.sharepoint.*` field strings. `TYPES_WITHOUT_A_CHANNEL` loses `onedrive`. The product names in copy are "Microsoft OneDrive (work or school)" and "Microsoft SharePoint", which Microsoft's guidelines allow as truthful compatibility statements.

15. **Icons are our own marks.** Microsoft's app icons need an express licence and the architecture icon set is restricted to diagrams and documentation, so neither can be shipped as a picker icon. Two original tiles in the house style of the existing marks (a cloud glyph for OneDrive, a site glyph for SharePoint), recorded in `ICONS.md` as original AI KB artwork with no Microsoft asset, and the type name beside the icon in the picker carries the product name. Reversible if Jason obtains a licence.

16. **Default-enabled, both types.** They join `DefaultConnectorTypes` with Notion, Confluence, GitHub and Bitbucket, which touches the same eleven-file surface the Bitbucket design lists (`.env.example`, `docker-compose.yml`, `helm/README.md`, the datasource tests, the docs pages, the upstream-review table, the changelog). A deployment that sets `AIKB_DATASOURCE_TYPES` must list them. The existing `onedrive` catalog entry is renamed "OneDrive (work or school)" and gains the capabilities; `sharepoint` gets priority 6 as well (the picker sorts by priority then type, so OneDrive precedes SharePoint).

## Data shapes

Credentials (both types): `{"tenant_id": "<GUID or domain>", "client_id": "<GUID>", "client_secret": "<secret>"}`.

Settings: OneDrive `{"user": "alice@contoso.com"}`; SharePoint `{"site_url": "https://contoso.sharepoint.com/sites/hr"}`.

Resource ids (`resource_ids`): `<driveId>` for a whole library or drive, `<driveId>:<itemId>` for a folder.

Connector cursor (`last_sync_cursor.connector_cursor`), schema version 1:

```json
{
  "schema_version": 1,
  "roots": {
    "b!abc:01XYZ": {"delta": "https://graph.microsoft.com/v1.0/drives/b!abc/items/01XYZ/delta?token=...", "next": "", "resync": false},
    "b!def": {"delta": "", "next": "https://graph.microsoft.com/v1.0/drives/b!def/root/delta?token=...", "resync": false}
  },
  "folders": {"b!abc:01FOLDER": {"parent": "b!abc:01XYZ", "name": "Policies", "root": "b!abc:01XYZ"}},
  "items": {"b!abc:01FILE": {"fp": "qx:ABC...|12345|b!abc:01FOLDER|handbook.docx", "parent": "b!abc:01FOLDER", "name": "handbook.docx", "root": "b!abc:01XYZ"}},
  "drives": {"b!abc": "Documents", "b!def": "Shared Documents"}
}
```

An unknown `schema_version` is `ErrInvalidConfig`; a cursor whose roots differ from the selection is reconciled per decision 8 before any delta call.

Fetched item (live): `ExternalID "b!abc:01FILE"`, `Title "handbook.docx"`, `FileName "Documents/Policies/handbook.docx"`, `Content <bytes>`, `ContentType` detected, `URL webUrl`, `UpdatedAt lastModifiedDateTime`, `SourceResourceID "b!abc:01XYZ"`, `Metadata {channel, msgraph_drive_id, msgraph_item_id, msgraph_path, msgraph_web_url}`.

## Known limitations

- Personal OneDrive accounts are not supported (decision 2).
- `Files.Read.All` is tenant-wide; the OneDrive connector reads one user's drive but the app registration can read any. The form hint says so and recommends a dedicated app registration.
- Shared folders from another drive (`remoteItem`), OneNote notebooks (`package`) and list items that are not files are not synced.
- The cursor grows with the number of files under the selected roots (about 550 bytes per file with SharePoint-length drive and item ids, including file and folder names, so about 5.5 MB at 10,000 files); a selection of more than about 10,000 files is better split across data sources.
- A folder rename or move does not rename the knowledge items under it; they take the new path when they next change.
- A data source in `full` sync mode runs every sync through `FetchFullStream`. Every root re-enumerates with a new generation, every file is re-fetched, unlisted items are tombstoned at the root's delta link, and a timed-out attempt resumes from its checkpoint. Incremental mode is the intended mode.
- Only the global Microsoft cloud; no national clouds, no SharePoint Server on premises.
- A SharePoint site is one data source; sub-sites need their own data source.
- The cursor in `last_sync_cursor` is readable through `GET /datasource/:id`: the `deltaLink` URLs (opaque position tokens that need a bearer token to use, not credentials) and every known file and folder name are visible to admins.

## Out of scope

- Delegated sign-in (authorization-code or device-code flow), personal OneDrive, refresh-token storage and rotation: a follow-up design once the `Connector` interface gains a credential writeback path.
- Change notifications (webhooks); the scheduler's polling plus delta is what Microsoft recommends for a periodic check.
- Permission (ACL) ingestion, which needs `Sites.FullControl.All`.
- SharePoint lists and pages, Teams channel files beyond their SharePoint library.
- A shared Graph client or capped reader across connectors.
